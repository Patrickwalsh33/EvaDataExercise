# ADR-001: Split the script into modules by responsibility

## Context

The inherited application is one 151-line script where reading, validating, calculating, presenting and coordinating are mixed together, mostly in one loop, and share global variables (see the [initial assessment](../initial-assessment.md)). Nothing can be tested without running the whole program, and the new country comparison needs the country and date of each EVA, which the current structure throws away. The brief also doesn't allow a single source file.

## Alternatives

- Keep one file but move the code into functions with a `main()`. This would make it testable, but AR2 doesn't allow a single file and all the responsibilities would still be together.
- Split by feature (a category module, a country module, a chart module), each doing its own loading, calculating and printing. This would repeat the loading and validation code in every module, and each module would still mix concerns.
- Use classes, or a library like pandas, for the analysis. This adds abstractions and a dependency the problem doesn't need, which the brief says to avoid.
- Split into modules by responsibility (loader, records, analysis, presentation, app), using plain functions and two small dataclasses.

## Decision

Split the script into five modules by responsibility inside an `eva` package. Keep the existing script as a thin entry point, and pass data between modules through function arguments and return values.

## Rationale

Each module matches one of the five responsibilities in AR1 and has one reason to change. The calculations become plain functions over a list of records, so they can be tested with hand-made data. Keeping the original script name means the run command stays the same and the file's Git history carries on. Plain functions are enough for an application this size, so no classes, frameworks or new dependencies are needed.

## Consequences

- Benefits: the analysis can be tested without files or console input, the new feature can be added mostly in `analysis.py` and `presentation.py`, and only `presentation.py` needs matplotlib.
- Limitations: there are six files instead of one, so following a run means starting at `app.py`. `app.py` has to pass data between modules explicitly.
- Trade-off: the modules share the `EvaRecord` and `CountrySummary` shapes, so changing a field means updating every module that uses it.
- Existing behaviour has to stay exactly the same, so the restructure keeps current quirks (like the case-sensitive country match and the crash when input ends). They'll be dealt with in a separate commit.
