# ADR-001: Split the script into modules by responsibility

## Context

The script I inherited does everything in one 151-line file: reading, checking, calculating, displaying and running, mostly inside one loop and all sharing global variables. None of it can be tested without running the whole thing, and the new comparison feature needs each EVA's country and date, which the current code throws away. The brief also says a single file isn't allowed.

## Alternatives

- Keep one file but tidy it into functions. That would make it testable, but it's still one file, which the brief rules out, and all the jobs would still be in one place.
- Split it by feature, with one file for categories, one for countries and one for the chart. Each would need its own loading and checking code, so there'd be a lot of repetition, and each file would still mix different jobs.
- Use classes, or a library like pandas. That's more machinery than a program this size needs, and the brief says to avoid unnecessary extras.
- Split it by job: reading, checking, calculating, displaying and running.

## Decision

Split the code into five modules by job, keep the original script as the starting point, and have the modules pass data to each other directly instead of through shared variables.

## Rationale

Each module lines up with one of the five jobs the brief lists, so each has one reason to change. The calculations become plain functions that take a list of records, so they can be tested with made-up data. Keeping the original script means you still run the program the same way and its history carries on. Plain functions are enough here, so there's no need for classes, frameworks or new libraries.

## Consequences

- Good: the calculations can be tested without files or typing, the new feature should mostly go into analysis.py and presentation.py, and only presentation.py needs matplotlib.
- Not so good: there are six files instead of one, so you have to start in app.py to follow a run, and data has to be passed around explicitly.
- The modules all rely on the same record format, so changing it means updating each one that uses it.
- The restructure has to keep behaviour exactly the same, including quirks like the crash when input runs out. Those get fixed in a separate commit.
