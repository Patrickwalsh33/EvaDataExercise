# ADR-002: Test the calculations directly with made-up records

## Context

The brief asks for automated tests of the comparison, one existing feature and some bad input or edge case, using known inputs and expected answers. The original couldn't be tested at all. After the restructure, the calculations are plain functions with no file or screen access, so I needed to decide how to test them.

## Alternatives

- Run the whole program with typed-in input and compare what it prints to saved output. That tests everything at once, but it needs the real data file and matplotlib, and when it fails it doesn't tell you which part is wrong.
- Test against the real data and check the real totals. Those numbers are hard to check by hand, and the real data has no ties or empty periods to test the edge cases with.
- Fake the keyboard and the file so presentation.py and app.py can be tested too. That's a lot more setup, and the tests would break whenever those modules are rewritten.
- Test records.py and analysis.py directly, using small lists of records I make up myself.

## Decision

Write unit tests with Python's built-in unittest for records.py and analysis.py, using small made-up data where I've worked out the answers by hand. Check the full program separately against saved output, as in the restructure check.

## Rationale

The restructure already separated the calculations from files and the screen, so testing them directly is the simplest option. Made-up data lets me test every rule exactly, like both end years counting, ties and countries with no EVAs, which the real data can't show. unittest comes with Python, so nothing needs installing, and the tests take a fraction of a second.

## Consequences

- Good: the tests are fast, don't need the data file or matplotlib, and when one fails it points straight at the problem. New edge cases are easy to add.
- Not covered: asking questions, re-asking after bad input and handling input running out aren't in the automated tests. I checked those by running the program myself.
- Made-up data doesn't prove the real file loads properly. Some of the record tests use entries in the same format as the real file, and the before-and-after check covers the rest.
