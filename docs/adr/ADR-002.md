# ADR-002: Test the analysis as plain functions with hand-made records

## Context

AR6 requires automated tests for the country comparison, one existing analysis operation and an invalid-input or boundary condition, using known inputs and expected results. The inherited script couldn't be tested at all, because importing it ran the whole program. After the restructure, records.py and analysis.py are plain functions with no file or console access, so I had to decide how to test them.

## Alternatives

- Run the whole program with piped input and compare the console output with saved files, like the AR5 check. This tests everything together, but depends on the real data file and matplotlib, and a failure doesn't show which calculation is wrong.
- Test against the real data file and check the real totals (for example USA 217 EVAs). These numbers are hard to verify by hand, and the real data has no ties or empty periods to test edge cases with.
- Use unittest.mock to fake input() and the file so presentation.py and app.py can be tested too. This needs more setup and ties the tests to how those modules are written.
- Unit-test records.py and analysis.py with small hand-made lists of records, using unittest.

## Decision

Write unit tests with Python's built-in unittest for records.py and analysis.py, using small hand-made datasets whose answers are worked out by hand. Check the whole program's behaviour separately against saved output (the AR5 check), not in the automated suite.

## Rationale

The restructure already made the analysis independent of files and the console, so testing it directly is the simplest option. Hand-made data lets every rule be tested exactly, including inclusive years, ties and countries with no EVAs, which the real data can't show. unittest comes with Python, so no dependency is added, and the tests run in a fraction of a second.

## Consequences

- Benefits: the tests are fast, don't need the data file or matplotlib, and a failure points straight at the function that's wrong. Edge cases are easy to add.
- Limitations: presentation.py and app.py (the prompts, re-asking for invalid input and the end-of-input handling) aren't covered by automated tests. I checked them by running the program instead.
- Trade-off: the hand-made data doesn't prove the real file parses correctly. The prepare_records tests use raw entries in the same format as the JSON file to cover part of this, and the AR5 check covers the rest.
